MisteR Dashboard

The open merge requests of a GitLab project on one page, with what each one waits for: pipeline, SonarQube, mutation testing, unresolved threads, lag behind the target branch.

Free software, MIT license. Created by Yann Robert.

Get it on GitHub Read the setup

  • Every signal in one row

    Pipeline, Sonar quality gate, mutation testing score, unresolved threads, approvals and how far the branch lags behind its target, for every open merge request.

  • Notified when it matters

    A browser notification when your merge request breaks or gets approved, or when the main branch's pipeline fails. Sounds too, one per refresh, the most important one.

  • Diffs that work offline

    Each merge request's diff is computed on your local clone, kept fetched in the background, so it stays readable during a GitLab outage. Commits grouped by push, review progress, line comments published to GitLab.

  • Claude Code prompts

    The AI button prepares a prompt for the merge request: fix what is red, review, explain. Actions come from a catalogue committed in your project; the prompt can be copied or launched in Orca.

  • Why did it take so long?

    The merged view replays the merge requests of the last 7, 30 or 90 days: development time, stabilization time, total duration.

  • Python 3.11+ only

    Standard library, no dependency, no build. A small server on 127.0.0.1 serves the page and relays GitLab and SonarQube, with a 30 s cache shared by all your tabs.

Start it

You need git, a local clone of the project to track, and a GitLab token from the glab configuration (glab auth login once).

git clone https://github.com/YannRobert/mr-dashboard.git
cd mr-dashboard
python3 mr_dashboard/server.py \
    --gitlab-host https://gitlab.example.com \
    --gitlab-project group/project \
    --pipeline-branch main \
    --repo-dir ~/src/project \
    --no-sonar --no-pit

Then open http://localhost:8765/. With SonarQube or mutation testing, the options name the server and the CI jobs; start.sh keeps the server running all day from a profile.

Screenshots you can share

Demo mode replaces people, titles, branches, labels and comments with fictitious values on screen, and keeps the same fake name for the same person across captures. The data underneath does not change: links and actions still act on the real merge requests.

Security

  • The server listens on 127.0.0.1 only and requires a Host of localhost or 127.0.0.1, so that a web page cannot reach it through DNS rebinding.
  • The GitLab and SonarQube tokens stay in the server process. The browser never sees them and never talks to GitLab or SonarQube directly.
  • Only reads are relayed. The only writes to GitLab are a line discussion, a reply, and resolving or reopening a thread, each validated before being forwarded.
  • Local actions require a dedicated header and an Origin of the dashboard itself.
  • Comments are rendered from GitLab's HTML after removing anything that could execute in the page.

The full security model is in the README; vulnerabilities are reported privately, as SECURITY.md explains.

Limits

  • One server tracks one GitLab project. For several projects, start one server per project, each on its own port.
  • The mutation testing score is read from a note that a CI job of your project posts on the merge request, in the documented format.
  • Launching a prompt in Orca needs the server under WSL with Orca on Windows. Elsewhere, prompts are copied.
